Comunicación entre servicios

Planificador de viajes — 3 microservicios orquestados desde el front

Versión 0.1 Estado Borrador Fecha 16/08/2026 Autor _______________

01Contexto y alcance

Este documento describe cómo se comunican hoy los componentes de la aplicación: un front y tres microservicios (MS1, MS2, MS3) que comparten una misma base MongoDB.

Provisorio. Todavía no está estandarizado el API Gateway, así que por ahora el front cumple el rol de orquestador: llama a cada microservicio en orden y va pasando el id que devuelve uno como entrada del siguiente. Cuando se defina el gateway, esta coordinación debería moverse detrás de él. Hasta entonces, este es el contrato vigente.

02Diagrama de comunicación

03Flujo paso a paso

  1. FRONT → MS1  Envía los datos de input cargados por el usuario.
  2. MS1 → MongoDB  Inserta el JSON en la collection solicitudes, referenciando el usuarioId.
  3. MS1 → FRONT  Responde 200 OK con el id1 del objeto creado.
  4. FRONT → MS2  Llama a MS2 pasándole el id1.
  5. MS2 → MongoDB  Lee la solicitud original por id1.
  6. MS2 → Web  Scrapea sitios de vuelos, hoteles y actividades turísticas.
  7. MS2 → MongoDB  Guarda los resultados en la collection scraping, referenciando el id1 de origen.
  8. MS2 → FRONT  Responde 200 OK con el id2 del registro generado.
  9. FRONT → MS3  Llama a MS3 pasándole el id2.
  10. MS3 → MongoDB  Lee los datos de scraping por id2.
  11. MS3 → Gemini  Envía todo el dataset a la Gemini API para generar 3 planes (vuelo + hotel + actividades).
  12. MS3 → MongoDB  Persiste los 3 planes en la collection planes, referenciando el id2.
  13. MS3 → FRONT  Responde 200 OK con el objeto de los 3 planes para renderizar.

06Pendientes por definir

  • API Gateway: estandarizar el punto de entrada y mover ahí la orquestación que hoy hace el front.
  • Manejo de errores: qué pasa si falla un paso intermedio (ej. MS2 responde error después de que MS1 grabó). ¿Se reintenta, se marca la solicitud, se hace rollback?
  • Idempotencia: evitar que un reintento del front duplique documentos (ej. si MS2 se llama dos veces con el mismo id1).
  • Timeouts: el scraping y la llamada a Gemini pueden ser lentos; definir tiempos máximos y comportamiento del front mientras espera.
  • Autenticación entre servicios: hoy el front reenvía IDs sin verificación fuerte entre MS. Definir cómo se validan las llamadas.
